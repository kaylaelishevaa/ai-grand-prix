Generated worlds now contain an LLM-authored **declarative geometry plan**, alongside their selected products in the same structured response. The model chooses the terrain outline, primitive arrangement, product supports, palette and atmosphere. It does not choose an authored room template or emit executable Three.js, shader code, URLs, or external assets.

A rebuild receives only its target `previousDistrict`: name, explanation, current eligible items and prior blueprint. Removed/owned/quarantined product anchors are excluded, and the whole reference is withheld if its source memories are no longer permitted. Other districts and private diary entries are not sent. This lets “make this warmer” edit the existing place instead of starting an unrelated scene; an explicit change of place or activity can replace the composition.

`SceneResult.blueprint` is optional only for legacy saved worlds and explicitly curated previews. New `/api/world` and `/api/scene` results require a valid version-1 blueprint. Initial world generation requests two distinct districts with 12–24 concise nodes each; validation permits 2–4 districts and 8–36 nodes per district. The world response has an 18,000-token ceiling and a 180-second timeout per provider attempt; ordinary structured requests retain their 90-second default. A semantic validation failure may retry once, while a transport timeout stops immediately. Rebuilds generate one replacement district and preserve its ID, creation date and independent diary snapshots.

`lib/scene-blueprint.ts` exports `WorldBlueprint` (also `SceneBlueprint`), `sceneBlueprintSchema`, `compileSceneBlueprint`, `validateSceneBlueprint`, `resolveBlueprintAnchors`, `blueprintPointInside`, `blueprintNodeCorners`, `blueprintAnchorFitsSupport`, and bounds constants. Vectors use `{x,y,z}` objects; outline points use `{x,z}`, avoiding unsupported tuple schemas.

| Field | Contract |
| --- | --- |
| `terrain` | 8–14 ordered vertices forming one simple polygon, area ≥8, x within ±3.8 and z within ±3.3. Depth .3–.9. Top surface fixed at y=.18. |
| `palette` | Six hex colors: `ground`, `structure`, `wood`, `foliage`, `accent`, `water`. |
| `atmosphere` | `skyTop`, `skyBottom`, `lightColor`, intensity .6–2, `timeLabel`, `weatherLabel`. These describe an imagined scene mood, not live weather. |
| `nodes` | 8–36 unique IDs; label; shape; material key; position, scale and Euler XYZ rotation; `motion: none/sway/float`; boolean `support`. |
| `anchors` | Exactly one per selected SKU. `supportId` or null; x/z; yaw in radians; scale .55–1.15. Product Y is computed by code. |

Allowed primitives are `box`, `cylinder`, `tapered`, `sphere`, `leaf`, `oval`, `arch`, `ring`, `wallArc`. Renderers normalize each primitive to a centered unit bounding box before applying the declared scale. All rotated corners must remain inside x±3.8, z±3.3, y=.18…3.8; scale components are at least .04. A node center must be over the terrain. The renderers reuse pooled geometries and materials; there is no arbitrary-code execution.

A product support must be a stationary, upright box or cylinder with x/z rotation zero. Its top is `position.y + scale.y / 2`. The shared helper resolves product height from that top, or from the terrain when `supportId=null`. Product geometry is bottom-aligned and normalized to XZ bounding diagonal ≤.68 and height ≤1 before anchor scaling. Validation reserves a circular radius of `.34 × scale` within the rotated support footprint and terrain edge. Product centers must be separated by at least the sum of those radii plus .10. Support tops must leave enough height for the inserted products. These rules keep the product anchors grounded and independently tappable.

Before persistence, a deterministic geometry compiler resolves physical contact and product packing within the model's design. It lifts floor-penetrating nodes in Y, keeping their shape, scale, rotation, X/Z position, terrain, palette and atmosphere unchanged. It preserves already valid product anchors exactly. Otherwise it tries the requested support at bounded scales down to .55, then nearby declared supports, then a bounded nearest-point search over clear authored terrain. Products retain their SKU and yaw; only anchor position, scale and support may change. Floor candidates avoid scenery bounds at product height. The compiler never invents products, adds decorative geometry, replaces the world with a template, or enlarges its stage. Unsafe terrain, horizontal bounds and ceiling violations remain errors.

The original strict validator is the final gate after compilation. Only the normalized, validated blueprint is cached and saved, and compiling that result repeatedly produces the same structure without drift. Remaining malformed plans report up to twelve measured bounds, support or separation problems together. The single repair attempt includes the previous structured answer plus those specific problems, preserving valid parts. Incomplete output receives a separate instruction to use fewer concise nodes and return complete JSON. Two failures return `WORLD_GENERATION_FAILED`: “I couldn’t shape that world yet. Try a simpler scene or a little more detail.” The old world remains intact; generation never silently substitutes a curated scene. Rendering fallback may draw the **same validated blueprint** in 2D when WebGL is unavailable.

In development, `.cache/geometry-validation.json` records only the most recent operation, time and bounded sanitized validation reason. It contains no raw model answer, user profile, labels or credentials and is never committed. Parser and schema errors are reduced to known issue codes, field paths and numeric bounds. Production and test environments do not write this diagnostic.

The request cache stores the exact structured response, including geometry. `DEMO_OFFLINE=1` replays only a matching validated cache entry; a miss or invalid entry fails before networking. Current surviving memory enters generation, while deleted/quarantined memory and private diary entries remain excluded. Product facts come only from the supplied catalog and review data. Synthetic SKUs use seeded evidence; sourced Coupang references retain historical-price provenance and never inherit synthetic reviews. Decorative geometry does not create new merchant claims.

`tests/fixtures/blueprint.ts` supplies a minimal synthetic plan for tests only. Production code never imports that fixture or uses it as a generation fallback. Tests cover unsafe fields, nonfinite values, self-intersections, rotated bounds, support/anchor grounding, exact SKU sets, distinct persisted plans, failed-generation preservation, memory deletion and offline replay with fake fetch only.
